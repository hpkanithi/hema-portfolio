ARCHITECTURE BREAKDOWN · COMPANY 01

Building Slack's Job Queue Pattern, on a $5 AWS Bill

Slack's original Redis-backed job queue hit a failure mode where memory pressure stopped both enqueue and dequeue operations. I rebuilt the durable-buffer pattern they adopted afterward, scaled down for a personal AWS environment.

AWS Terraform ECS SQS Redis CloudWatch
Company 01 / Slack Architecture · Infrastructure · Failure Testing
QUICK SUMMARY

In 2016, Slack's job queue deadlocked because its only storage was memory-limited Redis, and removing a job required a little memory it no longer had. Slack fixed the design by putting Kafka in front of Redis as a durable, disk-backed buffer. I rebuilt that same pattern small: a web service enqueues to SQS, a worker processes the queue and writes to Redis, and killing the worker delays messages instead of losing them.

01

THE FAILURE

The production problem

In 2016, a database slowdown made Slack workers dequeue more slowly than the web application could enqueue. Redis kept filling until it exhausted its available memory.

The interesting failure was what happened next: dequeuing itself required a small memory allocation. Once Redis had no memory left, the queue could not reliably remove old jobs to free space.

CORE FAILURE MODE Memory pressure did not just slow the queue — it prevented the queue from recovering itself.

This project is part of a portfolio series where I rebuild patterns from publicly documented company architectures at a scale I can realistically run myself.

This is a reverse-engineering exercise based on publicly available engineering material. It does not claim to represent Slack's current production implementation.

02

THE ORIGINAL PATTERN

What Slack built

Slack's asynchronous job system handled work that did not belong inside the web request path, such as push notifications, link unfurls, and search-index updates.

The original queue ran entirely on Redis and eventually hit the deadlock described above.

The redesign did not simply remove Redis. Slack placed Kafka in front of it as durable buffering, with small services moving jobs between Kafka, Redis, and the existing worker fleet. The architectural change separated durable ingestion from the in-memory queue used by workers.

04

TRADEOFFS

Choices I made on purpose

QUEUE

SQS instead of Kafka

Kafka would be operationally excessive for this workload. SQS provides the durable buffering behavior I need without introducing a distributed broker simply because it sounds more impressive.

COMPUTE

ECS on EC2 instead of Fargate

I chose the harder path deliberately: launch templates, an Auto Scaling Group, and an ECS capacity provider rather than delegating the compute layer entirely to Fargate.

NETWORKING

One NAT Gateway

This is a deliberate cost tradeoff. A production design would normally avoid making egress dependent on a single NAT Gateway, but that level of redundancy is difficult to justify for a temporary portfolio environment.

FAILURE HANDLING

DLQ from the first apply

Poison messages are expected failure cases in queue consumers. The worker can receive and delete from the queue, while the web task can only send to it, keeping IAM responsibilities separated.

05

PROVING THE DESIGN

Failure testing

TEST 01

Kill the worker

I scaled the ECS worker service to zero, then posted twenty messages. With no consumer available, the requests still returned successfully and the messages accumulated safely in SQS instead of disappearing.

RECOVERY

Restore the worker

I brought the worker service back online. As processing resumed, the queue depth dropped progressively from 20 to zero.

VALIDATION

Verify the messages survived

A drained queue alone does not prove successful processing. I queried the application afterward to confirm that the messages reached the downstream store successfully.

TEST 02

Poison message

Next I intentionally submitted a message the worker was designed to reject. Rather than allowing an infinite retry loop, SQS redelivered the message three times before moving it into the dead-letter queue.

RESULT Worker downtime created backlog, not data loss. Recovery drained that backlog successfully, while poison messages were isolated instead of retrying forever.
06

REAL BUILD PROBLEMS

What actually broke

01
CONTAINER ARCHITECTURE

ARM64 image mismatch

The ECS instances use Graviton, while my laptop initially built the Docker image for its own architecture. 

CannotPullContainerError:
no matching manifest for linux/arm64/v8

A plain docker build --platform linux/arm64 still did not solve the issue in my local setup. Building through a real multi-platform buildx builder and pushing from that build path produced the correct image.

02
ECS DEPLOYMENT

RESOURCE:ENI during rolling deployment

My Auto Scaling Group had exactly enough capacity for the running tasks and no spare room for a normal rolling update.

ECS attempted to start a replacement task before stopping the old one and could not allocate the required ENI. 

deployment_maximum_percent         = 100
deployment_minimum_healthy_percent = 0
availability_zone_rebalancing      = "DISABLED"

The deployment strategy now replaces tasks one-for-one instead of requiring temporary capacity for both generations.

07

LIMITS

Where this falls apart at Slack scale

The architecture pattern transfers. The sizing does not.

A personal AWS account, a small ECS cluster, one VPC, and one NAT Gateway are intentionally nowhere near Slack's operating scale.

01

A tiny ECS Auto Scaling Group cannot absorb real Slack-scale traffic.

02

A single SQS-based design would require significant rethinking, partitioning, or a broker architecture suited to sustained massive parallelism.

03

One NAT Gateway creates an availability tradeoff that would not be acceptable in a serious production design.

04

This build has no multi-region or cell-isolation story.

THE REUSABLE LESSON Durable buffering isolates request-time producers from slower or temporarily unavailable workers. Infrastructure sizing is a separate decision driven by actual load.

Try it yourself

The entire environment is provisioned with Terraform. The most useful test is simple: stop the worker service, send messages, confirm that SQS retains them, restore the worker, and watch the backlog drain.
